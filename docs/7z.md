# Encrypted 7z implementation and verification

The app keeps libarchive for ZIP, plain 7z, and filtered TAR. Encrypted 7z uses
Apache Commons Compress **1.28.0** and XZ for Java **1.10**. It writes LZMA2 data
compressed with preset 3 (a 4 MiB dictionary), encrypted with the standard 7z
AES-256/SHA-256 codec. The password is encoded as UTF-16LE and uses 2^19 SHA-256
rounds, matching 7-Zip's default. Each entry and the optional encrypted header
get independently generated 16-byte salts and IVs.

## Sources checked

- [7-Zip's format specification](https://github.com/ip7z/7zip/blob/main/DOC/7zFormat.txt)
  defines `kEncodedHeader`, `PackInfo`, `Folder`, `CodersUnpackSize`, and the
  start/header CRCs.
- [7-Zip's AES codec](https://github.com/ip7z/7zip/blob/main/CPP/7zip/Crypto/7zAes.cpp)
  defines the password derivation, 19-bit cycle exponent, and salt/IV properties.
- [Commons Compress 1.28.0 SevenZOutputFile](https://github.com/apache/commons-compress/blob/rel/commons-compress-1.28.0/src/main/java/org/apache/commons/compress/archivers/sevenz/SevenZOutputFile.java)
  supports AES output since 1.23.0 but has no header-encryption switch.
- [Commons Compress 1.28.0 AES256SHA256Decoder](https://github.com/apache/commons-compress/blob/rel/commons-compress-1.28.0/src/main/java/org/apache/commons/compress/archivers/sevenz/AES256SHA256Decoder.java)
  supplies both encoding and decoding; the app uses its encoder, including the
  format's zero-padding behavior, without introducing a separate crypto codec.
- [Commons Compress 1.28.0 AES256Options](https://github.com/apache/commons-compress/blob/rel/commons-compress-1.28.0/src/main/java/org/apache/commons/compress/archivers/sevenz/AES256Options.java)
  has an explicit salt/IV constructor. `AndroidSevenZEncryption` is a small bridge
  in that package to use Android's `SecureRandom` instead of the public password
  constructor's `SecureRandom.getInstanceStrong()` (only available from API 26).
  This bridge intentionally depends on the pinned version's package-private API;
  inspect these sources and rerun both interoperability tests when upgrading it.
- [libarchive's 7z reader](https://github.com/libarchive/libarchive/blob/master/libarchive/archive_read_support_format_7zip.c)
  detects AES but cannot decrypt it. The actual bundled library,
  **libarchive-android 1.1.7 / libarchive 3.8.8**, was also exercised: the header
  encrypted fixture reports `The archive header is encrypted, but currently not
  supported`; the content-only fixture reports `Damaged 7-Zip archive` before
  returning an entry. Consequently, any libarchive read error on a verified 7z
  signature is retried with Commons, which still validates the archive's CRCs.
- [Google's desugaring changelog](https://github.com/google/desugar_jdk_libs/blob/master/CHANGELOG.md)
  distinguishes the standard and NIO configurations. Commons 1.28.0 uses
  `java.nio.file.attribute.FileTime`, so the app uses
  **desugar_jdk_libs_nio 2.1.5**. The standard 2.1.5 configuration was inspected
  and does not rewrite this class, despite including it in the implementation JAR.
  The built APK was inspected too: Commons' three date fields reference
  `Lj$/nio/file/attribute/FileTime;`, and a DEX includes that class definition.
  The existing API 24 minimum for creating 7z is retained; encrypted ZIP on API 23
  continues to use libarchive.
- [XZ for Java's licensing statement](https://tukaani.org/xz/java.html) specifies
  0BSD for version 1.10; earlier releases were public domain. The app's licenses
  page includes the actual 0BSD text and Apache notices for Commons dependencies.

## Output, failure handling, and reading

`EncryptedSevenZOutputFile` uses Commons for entry compression, metadata, and
checksums. With filename encryption selected, its channel buffers only the final
metadata emitted by `finish()`, encrypts that metadata, and writes a standard
encoded-header descriptor. Plaintext filenames are never written to that output.
The writer handles short writes, propagates finalization errors, checks thread
interruption, and does not close a channel owned by the caller.

Encrypted 7z requires rewriting its 32-byte signature. Linux file destinations
support that directly. FTP may truncate on a restarted `STOR`, while document and
WebDAV providers may disallow random writes. For non-Linux destinations the file
job builds the same final encrypted archive in private app cache and then copies
it sequentially to the `CREATE_NEW` target. The temporary archive is removed in
`finally`; failure/cancellation also removes the incomplete target. This adds a
temporary archive's disk usage and one copy only for those destinations. No source
contents are staged in plaintext; filename visibility in the temporary archive
matches the user's filename-encryption option.

The reader retries saved passwords with the newest first and maps missing/wrong
passwords to `ArchivePasswordRequiredException`, preserving the existing password
dialog. When multiple passwords exist, the requested entry is first read through
a fixed-size buffer to verify its CRC before selecting a password, then reopened.
This extra read is necessary because an AES+Copy stream can otherwise return
incorrect bytes until the CRC check at EOF; no plaintext temporary file is used.
It retains empty entries, Unix type/mode attributes, and symbolic links.
The decoder memory limit is one third of the process's maximum heap, bounded to
16–128 MiB. A provider that only supplies input streams is copied to a private
temporary file as an already encrypted archive, then removed on close.

## Reproducible checks

Run with a JDK 11+ and official `7zz` on PATH:

```sh
python tools/verify_7z.py --java-home /path/to/jdk
```

The script downloads the exact Maven dependencies over HTTPS, verifies Maven's
published checksums, compiles the real Java writer, and runs it with a 96 MiB heap.
Its default work directory is `~/tmp/materialfiles-7z-check`, keeping generated
archives and downloaded libraries out of the repository.

Successful writer runs used **7-Zip 26.04 (arm64)** and covered:

- Correct, incorrect, and missing passwords for content and header encryption.
- Visible names with content-only encryption and hidden names with header
  encryption, including checking raw bytes for leaked UTF-16LE names.
- Chinese names/passwords, an emoji in the password, multiple files, empty files
  and directories, and Unix symbolic-link metadata.
- A source whose size was initially zero but subsequently produced data.
- A 16 MiB stream, extracted and checked byte-for-byte by official 7-Zip.
- A provider that writes only seven bytes at a time, and a completed archive
  copied through a destination that rejects all seeks/reads and only accepts
  sequential writes of thirteen bytes at a time.
- Cancellation, explicit abort, and an injected signature-write failure; the
  failure is reported and plaintext names remain absent from the output.

After `assembleDebug`, also run the actual compiled Kotlin reader:

```sh
python3 tools/verify_7z_reader.py \
  --gradle-home /path/to/gradle-cache \
  --android-jar /path/to/android-sdk/platforms/android-37.2/android.jar \
  --java-home /path/to/jdk \
  --seven-zip /path/to/7zz \
  --writer-fixtures ~/tmp/materialfiles-7z-check/fixtures
```

This second tool reads the existing Gradle dependency cache, loads the real
compiled `SevenZArchiveReader`, `ReadArchive.Entry`, permission conversions, and
`ArchivePasswordRequiredException`, and runs them with a 96 MiB heap. Only Android's
POSIX `OsConstants` methods and the provider boundary are substituted for the JVM;
the injected channels read actual archive files. It refuses stale reader bytecode.

The final run on 2026-10-09 passed **29 / 29 checks**, using archives produced by
official **7-Zip 26.04**, as well as the app writer's fixtures. It verifies both
directions: the app's archives are extracted by official 7-Zip, and official
solid LZMA2/AES and Copy/AES archives are read by the app's actual Kotlin reader.
Coverage includes correct/missing/incorrect passwords; fallback from a wrong
recent password to a correct older password (including AES+Copy); Chinese paths,
passwords, and emoji; exact contents including the 16 MiB stream; empty files and
directories; Unix modes, modification times and symlink targets; cancellation and
ordinary I/O failures retaining their exception type; and releasing the owner
exactly once even when archive close fails. The test artifacts and complete
`results.log` are kept under `~/tmp/materialfiles-7z-reader/run-*/`.

These JVM/CLI checks complement the Android build and lint checks. They do not
exercise Android's notification UI, an actual FTP/WebDAV server, or an API 24/25
device.
