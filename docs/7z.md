# Archive engines and verification

All 7z reading and writing uses the official **7-Zip 26.04 C++ archive handler**,
compiled into `libsevenzip.so`. The reader routes by the six-byte 7z signature,
including unencrypted and renamed archives. Other archive formats use
**libarchive-android 1.1.7 / libarchive 3.8.8**. Apache Commons Compress and XZ for
Java are no longer application dependencies. Other Commons libraries remain
transitive dependencies of unrelated network providers.

## Compression options

| Format | Contents | Password encryption |
| --- | --- | --- |
| ZIP | Files and directories | AES-256 |
| 7z | Files and directories, solid LZMA2 | AES-256; optional filename encryption |
| TAR | Files and directories | Unavailable in this format |
| TAR.GZ, TAR.BZ2, TAR.XZ | Files and directories in a compressed TAR | Unavailable in these formats |
| GZIP, BZIP2, XZ | One regular file | Unavailable in these formats |

There is no encryption-method selector. ZIP and 7z use AES-256 whenever a password
is supplied. The ZIP writer selects libarchive's `encryption=aes256` option; 7z
uses the official AES codec, key derivation and random salt/IV generation.

| Preset | ZIP / gzip / bzip2 level | 7z level / dictionary | XZ level |
| --- | --- | --- | --- |
| Speed | 1 | 1 / 4 MiB | 1 |
| Standard | 5 | 5 / 16 MiB | 5 |
| Quality | 9 | 9 / 32 MiB | 7 |

The 7z writer uses at most two encoder threads. XZ uses one. The more conservative
XZ quality level avoids the 64 MiB dictionary and substantially greater encoder
memory required by level 9. Plain TAR has no compression stage.

Splitting offers no split, 5 MB, 10 MB, 50 MB, or a custom size; sizes use
1 MB = 1,048,576 bytes. Volumes are raw consecutive chunks named
`archive.ext.001`, `.002`, etc., compatible with 7-Zip's split-stream convention.
These are not ZIP multi-disk records. Open or extract the `.001` file while all
volumes are in the same directory. Browsing and extraction join the volumes
through one seekable channel, or through a sequential stream for providers that
cannot seek. No plaintext contents are staged for extraction.

**Delete source files after compression is optional and off by default.** It runs
only after the archive is finalized and every destination volume has closed
successfully. Compression errors, destination conflicts and cancellation retain
the sources. Deletion uses snapshots of the inputs actually archived, checks their
size, modification time and identity again, and deletes known paths individually.
New or changed files are retained; a newly added child also prevents deletion of
its parent directory. A deletion failure leaves the completed archive available.
Creating an archive inside one of its source directories is rejected.

## Extraction and failure handling

The file menu and selection menu provide extraction into the current folder or
an independent folder named after the archive. Existing conflict handling applies.
For a selection from one 7z archive, regular entries are processed in archive
order by one native `Extract` call. A 64 KiB pipe connects the decoder to the
existing copy/progress code. This decodes shared solid blocks once. Directories,
skip decisions and renamed destinations retain their normal file-job behavior.
The session belongs to one file job; another reader does not consume its stream.

Saved passwords are tried newest first. Missing/incorrect passwords become the
same `ArchivePasswordRequiredException` used by the password dialog, attached to
the virtual `ArchivePath`. That path identifies the physical archive and stores
the password for retry. Passing the physical path instead caused the previous
extraction crash. Header-encrypted archives can request a password during the
scan and restart the scan after a successful response. AES+Copy may report a
wrong password only at its final CRC; that failure also removes partial output.

JNI preserves provider I/O exceptions and translates native allocation failures
into I/O errors. The decoder's native allocation budget is one third of the Java
maximum heap, bounded to 16–128 MiB; the encoder has a 512 MiB allocation ceiling.
The budget is propagated to official 7-Zip worker threads. These are allocation
limits, not a fixed reservation or a whole-process RSS limit. Cancellation keeps
the thread's interrupted flag and releases native objects and input streams.

Writing 7z requires rewriting its signature header. Splitting and non-Linux
destinations therefore finalize an archive in private application cache before
copying the completed archive sequentially. The temporary file contains the
archive in the selected encryption mode; it is removed in `finally`. A
stream-only input provider similarly stages the compressed source for random
reads. `ArchiveOutput` uses `CREATE_NEW`, tracks only files created by that
operation, and rolls them back on failure, including a failed destination close.
Existing files are not overwritten by rollback.

## Vendored source and native build

The selected upstream files under `app/src/main/jni/7zip` are unmodified. Their
version, release URL, source-archive SHA-256 and individual checksums are recorded
in `SOURCE.json`. The release archive is:

`https://github.com/ip7z/7zip/releases/download/26.04/7z2604-src.tar.xz`

SHA-256: `9691944c0fe0d01bb49373a704fb983fd33bc98b1738695179dfbf99ac1734f6`

`sevenzip_sources.list` selects the handler and codecs used by the JNI library.
The native target does not start a CLI, load external codecs, or include RAR
handlers. Its allocator and Windows compatibility wrappers live outside the
upstream directory. CMake builds it with a static C++ runtime, hidden internal
symbols, a version script and 16 KiB page alignment. Standard Gradle Android NDK
builds include the native target automatically. `build-sevenzip.py` can also build
the same target using a Termux-hosted Clang and an NDK sysroot; see its `--help`.

The app's license page includes 7-Zip's LGPL 2.1 notice. The full upstream license,
format specification and release documentation are retained under `7zip/DOC`.
Relevant implementation references include upstream `Archive/7z/7zHandler.cpp`,
`7zExtract.cpp`, `7zUpdate.cpp`, and `Crypto/7zAes.cpp`, and libarchive's
`archive_write_set_format_zip.c` and `archive_write_add_filter_{gzip,bzip2,xz}.c`.

## Reproducible APK checks

Build an unminified debug APK, then run from Android/Termux with the same JDK
environment used for the build:

```sh
python3 -B tools/verify_archives.py \
  --gradle-home /path/to/gradle-cache \
  --android-jar /path/to/android-sdk/platforms/android-37.2/android.jar \
  --java-home /path/to/jdk \
  --apk app/build/outputs/apk/debug/app-debug.apk
```

The runner extracts the APK's actual native libraries, compiles only the harness,
converts it to DEX with D8, and runs it with Android `app_process`. Application
classes and dependencies are loaded from the APK. It records the APK SHA-256,
archives, compiler output and runtime logs under `~/tmp/materialfiles-archive-check`.
It neither installs the APK nor changes application data.

`--suite native`, `--suite password`, `--suite volumes` and `--suite formats`
select individual groups. The older `verify_7z.py`, `verify_7z_reader.py` and
`verify_7z_password_flow.py` names remain as entry points to these APK tests.
`--fixtures` reuses official 7zz fixtures, and `--writer-fixtures` can additionally
test archives produced by the previous app writer.

Coverage includes official-to-app and app-to-official 7z compatibility; all
presets and encryption modes; Unicode names/passwords; empty files/directories;
symlinks, Unix modes and timestamps; large data; short I/O; source-close errors;
decoder memory limits; interruption; password-dialog path operations; solid
batch ordering, skipping, retry and isolation; late CRC cleanup; split boundaries,
random access, truncation, collisions, rollback and stream-only providers.

Validation on 2026-10-09 used Android API 35 and official 7-Zip 26.04 on ARM64.
The final APK passed **32 native engine checks**, **22 password/batch checks** and
**24 format/source-deletion checks**, with JNI checking enabled. Official 7-Zip
also verified **11 native-writer archives** and **23 format/split archives**,
including ZIP AES-256 and all three presets. Split-volume tests passed **27 checks**,
including 5/10/50 MiB boundaries and failure rollback.
For the solid fixture, extracting the selected entries together read 544 compressed
bytes; separate extraction read 2,176 bytes. This measures compressed reads for
that fixture.

`assembleDebug` and `lintDebug` passed. The APK contains neither Commons Compress
nor XZ-for-Java classes. The native library also compiled and linked for ARMv7,
x86 and x86-64; all four ABI outputs have 16 KiB load alignment and depend only on
system libraries. Only ARM64 received runtime validation.

Final ARM64 debug APK SHA-256:
`2e820a17c2a7e22aae7dee5961a9530f55dcf2756c03d938fa0a93445ca27ced`.

These harnesses exercise real Android DEX and native engines, but do not render
the dialogs, drive touch gestures or notifications, or contact an actual remote
document/FTP/WebDAV provider. Device UI and other Android ABI/API combinations
require their own integration runs.
